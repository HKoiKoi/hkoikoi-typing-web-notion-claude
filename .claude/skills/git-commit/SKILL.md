# Git 커밋

변경사항을 분석해 이 프로젝트의 커밋 관례에 맞는 한국어 커밋 메시지를 만들고, 사용자가 커밋을 요청했다면 커밋까지 수행한다. 커밋 기록은 나중에 변경 이유를 추적하는 자료이므로, 일관된 형식과 "한 커밋 = 한 논리적 변경"이 핵심이다.

## 워크플로

1. **현재 상태 파악** (병렬 실행 가능)
   - `git status`: staged / unstaged / untracked 구분
   - `git diff --staged`: 커밋 대상. staged가 없으면 `git diff`로 전체 변경 확인
   - `git log -5 --format=%B---`: 최근 메시지 스타일 확인. 이 저장소의 관례가 이 문서보다 우선한다.
2. **분석**: 무엇이 바뀌었는지(기능 추가 / 버그 / 리팩토링 / 문서 / 설정)와 왜 바뀌었는지 파악한다.
3. **분리 판단**: 성격이 다른 변경(예: 기능 + 문서 + 설정)이 섞여 있으면 커밋을 나눌 것을 제안하고, 파일 단위로 어떻게 묶을지 제시한다. 나누면 `git revert`·리뷰·이력 검색이 쉬워진다.
4. **메시지 작성**: 아래 규칙을 따른다.
5. **커밋 수행** (사용자가 커밋을 요청한 경우에만)
   - 대상 파일을 이름으로 지정해 `git add <파일...>` 한다. `git add -A`/`.`는 의도치 않은 파일(비밀 키, 빌드 산출물)이 섞일 수 있어 피한다.
   - `.env*`, 키/토큰/인증서 파일이 변경 목록에 있으면 제외하고 사용자에게 알린다.
   - 여러 줄 메시지는 HEREDOC으로 전달한다.
     ```bash
     git commit -m "$(cat <<'EOF'
     feat: 제목

     - 본문
     EOF
     )"
     ```
   - pre-commit hook이 실패하면 원인을 고치고 **새 커밋**을 만든다. 실패한 커밋은 만들어지지 않았으므로 `--amend`는 직전의 다른 커밋을 덮어쓰게 된다.
   - 커밋 후 `git status`로 결과를 확인한다. `push`는 사용자가 따로 요청할 때만 한다.
6. 커밋 요청이 아니라 "메시지만 만들어줘"라면 메시지를 코드블록으로 제시하고 멈춘다.

## 메시지 형식

```
<타입>(<스코프>): <제목>   ← 스코프는 선택, 없으면 `<타입>: <제목>`

<본문> (선택)

<트레일러> (선택)
```

- **스코프는 필요할 때만 쓴다.** 변경이 한 영역에 한정되어 있고, 스코프가 있으면 커밋 목록에서 영향 범위를 바로 알 수 있을 때 붙인다 (`feat(layout): 모바일 내비게이션 추가`). 변경이 여러 영역에 걸치거나 제목만으로 범위가 분명하면 생략한다. 이 저장소의 기존 히스토리는 스코프 없이 쓰였으므로, 애매하면 생략하는 쪽이 일관성이 높다.
- **스코프 이름**은 소문자 영문 한 단어로, 아래 영역 중에서 고른다. 새 이름을 만들기 전에 `git log`에서 이미 쓰인 스코프를 확인해 같은 영역에 다른 이름이 생기지 않게 한다.

  | 스코프 | 영역 |
  | --- | --- |
  | `ui` | `src/components/ui/` (shadcn 컴포넌트) |
  | `common` | `src/components/common/` |
  | `layout` | `src/components/layout/` |
  | `app` | `src/app/` 라우트·페이지 |
  | `config` | `src/config/`, `next.config.ts` 등 설정 |
  | `deps` | 의존성 추가/업데이트 |
  | `hooks` | `src/hooks/` |

- 스코프는 하나만 쓴다. 두 개 이상이 필요하면 커밋을 나눌 신호인지 먼저 따져 본다.
- **제목**: 50자 안팎, 마침표 없음, 명사형/간결체로 끝낸다 ("추가", "수정", "교체", "적용"). 한국어에서 "추가해라" 같은 명령형은 어색하고, 기존 히스토리도 명사형이다. "추가했음"처럼 과거형도 쓰지 않는다.
- **본문**: 제목만으로 의도가 전달되지 않을 때만 쓴다. 한 줄 띄우고 불릿으로 "무엇을, 왜" 위주로 적는다. 변경 파일 목록을 나열하는 것은 diff가 이미 보여주므로 불필요하다.
- **트레일러**: 이슈 참조는 `Fixes #123`. 세션이 커밋 attribution 트레일러(예: `Co-Authored-By: ...`)를 지정했다면 맨 끝에 빈 줄을 두고 그대로 추가한다. 이 저장소의 Claude 작성 커밋에는 이 트레일러가 붙어 있다.

## 타입

| 타입 | 사용 시점 |
| --- | --- |
| `feat` | 새로운 기능·화면·컴포넌트 추가 |
| `fix` | 버그 수정 |
| `docs` | 문서 수정 (README, CLAUDE.md 등. 코드 변경 없음) |
| `style` | 포맷팅 등 동작에 영향 없는 스타일 변경 |
| `refactor` | 동작 변경 없는 구조 개선 |
| `test` | 테스트 추가/수정 |
| `perf` | 성능 개선 |
| `chore` | 의존성, 빌드/도구 설정, `.gitignore`, `.claude` 설정 등 |

타입이 애매하면 "사용자에게 보이는 동작이 바뀌었는가?"를 기준으로 한다. 바뀌었다면 `feat`/`fix`, 아니라면 `refactor`/`chore`/`docs`다.

## 예시

| 변경사항 | 커밋 메시지 |
| --- | --- |
| 공통 컴포넌트 추가 | `feat(common): EmptyState 컴포넌트 추가` |
| 한 영역의 버그 수정 | `fix(layout): 모바일 내비게이션이 닫히지 않는 문제 수정` |
| 여러 영역에 걸친 변경 (스코프 생략) | `feat: 앱 라우트(홈, 컴포넌트, 에러/로딩/404) 구성` |
| 의존성 | `chore(deps): next-themes, sonner 추가` |
| 문서 | `docs: CLAUDE.md에 프로젝트 구조 및 명령어 추가` |
| 설정 | `chore: .gitignore에 Playwright 산출물 폴더 추가` |

본문이 필요한 경우:

```
fix: 토큰 만료 시 무한 리다이렉트 해결

- 갱신 로직이 만료 시각을 잘못 계산해 로그인 페이지로 반복 이동하던 문제 수정
- 만료 직전 요청에서도 갱신되도록 여유 시간 추가

Fixes #456
```

## 피해야 할 메시지

- 모호함: `fix: 버그 수정`, `update code` (무엇이 바뀌었는지 알 수 없음)
- 여러 변경 혼합: `feat: 로그인 추가 및 버그 수정 및 문서 업데이트` (나눠서 커밋)
- 지나치게 긴 제목: 세부 내용은 본문으로 보낸다.
